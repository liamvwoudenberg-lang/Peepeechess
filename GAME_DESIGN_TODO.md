# Peepeechess — game design and release polish TODO

Audit baseline: `f37a7bdf4cc05b11c338d6579ba73d3f757a18ed` (Godot 4.6.3, native client; includes the draft UI and courtyard work). This is a prioritized working backlog, not a claim that every possible issue has been found. The legacy React/Capacitor game is a separate product path and should be reviewed independently if it remains supported.

**Evidence:** source and current project documentation were reviewed; earlier software-rendered screenshots in `docs/ui/` were inspected as historical references, not as proof of the current appearance. No physical Android/Windows device, real GPU, controller, live WAN session or complete human playthrough was available for this audit. Items marked **Verify** are questions to test, not confirmed defects. Older documents may describe superseded implementations: check the referenced code before changing anything.

## P0 — Blocks a credible public release

- [ ] **Investigate Android exits** after the opening screen, in menus and when starting both 2D and 3D games (reported by player). Capture device model, Android version, steps and `adb logcat`/tombstone; reproduce on several GPUs. The texture-size reduction and low default reduce memory pressure but do not establish or prove a fix for the actual crash. Check startup, pause/resume, repeated games and memory after leaving a match. Evidence: `godot/paladins/paladin_model.gd`, `godot/tests/paladin_memory_test.gd`, `godot/ui/application_settings.gd`.
- [ ] **Verify both shipping builds on real hardware.** Install and play the actual Windows executable and APK, exercise both chess views, battles, audio, window changes, controller and touch; record device models, frame times, memory and crash logs. Debug-signed APK and unsigned Windows builds are test artifacts, not store releases. Evidence: `docs/application/TESTING_GUIDE.md`, `godot/export_presets.cfg`.
- [ ] **Stabilize online combat and reconnection testing.** The project reports intermittent prediction, stale-input and handshake test failures; reproduce under controlled latency/loss and distinguish a product bug from test timing. Test reconnects, timeouts, resume, duplicate results and Windows–Android sessions on a real network. Evidence: `DEVELOPMENT_STATUS.md` (timing report), `docs/network/ONLINE_COMBAT.md`, `godot/combat/NETWORKING.md`.
- [ ] **Complete release operations.** Set up real release signing, verified distribution, upgrade/install testing, versioning and a supportable download path; make the current platform and online-host requirements clear before installation. Confirm production backend, backups and monitoring. Evidence: `docs/application/EXPORTS.md`, `docs/development/RELEASE_CHECKLIST.md`.

## P1 — Presentation and player experience

### Characters, motion and combat

- [ ] Replace or refine the visibly procedural combat animation: unique readable idle, walk/run, true sideways strafe, guard, parry, dodge, recovery and defeat for each role. Preserve animation timing against actual hit windows. Current strafe reuses walking; block and attack poses are simplified. Evidence: `docs/ui/PALADIN_COMBAT.md`, `godot/paladins/paladin_clips.gd`.
- [ ] Replace the plain procedural box sword with finished role-appropriate weapons and coherent left-hand equipment; check materials, grips, scaling, team contrast and hit effects in close-up. The current common sword is documented in `docs/ui/PALADIN_COMBAT.md`.
- [ ] **Verify** visual combat feedback matches the authoritative simulation: hit location/reach, startup, contact, block/parry, cooldown, guard break and damage; improve telegraphs without obscuring fighters. Test all six roles, both teams, different cameras and frame rates. Inspect the older rig audit before generalizing findings to Meshy models: `godot/assets/combat/ANIMATION_INTEGRITY.md`.
- [ ] Polish transitions on capture and return: check hands/feet against ladder, shaft, trapdoor and floor; review stowing, drop/landing, camera cutaways and winner return in motion. Keep the existing underground arena and ladder sequence. Evidence: `godot/world/pit_sequence.gd`, `godot/world/README.md`; the newest branch has updated ladder animation.
- [ ] Avoid board animation intersections on castling and long sliding moves; ensure pieces remain identifiable and the final positions match the chess state even when animations are interrupted. Evidence: `docs/ui/PALADIN_BOARD.md`, `godot/boards/board_3d.gd`.
- [ ] Human-playtest combat pacing and balance across all pairings, abilities, attacker/defender outcomes and King's last stand. Existing calibration is bot-measured; do not treat bot win rates as proof of fair or enjoyable human play. Evidence: `godot/combat/BALANCE.md`, `DEVELOPMENT_STATUS.md`.

### Camera, board and environment

- [ ] **Verify** the enlarged pieces and tighter board framing on desktop, narrow phones and tablets, both orientations and all camera angles: no clipping, overlapping silhouettes, off-screen squares or obscured legal moves. Check every class at opening, movement, promotion and capture. Evidence: `godot/boards/paladin_piece.gd`, `godot/world/camera_rig.gd`.
- [ ] Make king/queen and all other roles immediately distinguishable from above in both teams and on both square colors. Validate crest legibility and selection/last-move/check markers at actual playing size, including color-blind settings. Project notes indicate color-blind settings do not yet cover all 3D highlights: verify the current implementation. Evidence: `godot/boards/piece_crest.gd`, `godot/boards/board_theme_view.gd`, `DEVELOPMENT_STATUS.md`.
- [ ] **Verify and polish** courtyard lighting, shadow length, dark-team visibility, material scale and seams at tactical and close-up camera distances; compare against the supplied medieval castle references. Check obstruction fading during orbit, zoom and battle transitions. Evidence: `godot/boards/courtyard_environment.gd`, `godot/boards/board_3d.gd`.
- [ ] Review camera comfort and continuity through orbit, zoom, combat and resize; verify walls/pillars do not hide fighters, particularly in split-screen. Test motion reduction and sudden changes of framing on mobile. Evidence: `godot/world/camera_rig.gd`, `godot/combat/presentation/third_person_camera.gd`.
- [ ] Bring online capture presentation to parity with the intended local trapdoor/arena return sequence, without delaying or altering server authority. Existing notes explicitly say the online pit path is not wired; recheck its current code and countdown/reconnect behavior before implementing. Evidence: `godot/world/README.md` (online path), `godot/network/client/online_combat_view.gd`.

### UI, navigation and accessibility

- [ ] Audit every menu, dialog and game mode for a consistent finished visual language: typography, icon weight, spacing, panel depth, selection/hover/focus/disabled states and useful empty/error/loading states. Play setup has documented old-style toggles and a missing queue spinner; verify against the current branch. Evidence: `godot/ui/application.gd`, `godot/ui/game_hud.gd`, `DEVELOPMENT_STATUS.md`.
- [ ] **Verify** immersive HUD at phone and desktop sizes, high UI scaling and all safe areas: chess toolbar/history/help must not bleed into combat; health, stamina, timer, ability icons, damage numbers, touch controls and result states must stay legible and avoid overlap. Exercise local split-screen and online views. Evidence: `godot/app/courtyard_combat_hud.gd`, `godot/app/combat_hud_installer.gd`.
- [ ] Complete keyboard, screen-reader, controller and touch accessibility review: visible focus, sensible navigation and back behavior, accessible text labels, adequate contrast and touch targets; do not rely on color alone. Verify F1/help can be opened and dismissed on each device. Evidence: `godot/ui/pad_ui.gd`, `godot/combat/presentation/control_overlay.gd`.
- [ ] Add clear, optional onboarding for chess movement, capture battles and controls; explain attacker/defender outcome rules, timer, stamina, abilities and network status at the moment they matter. Test first-time players without relying on permanent instructions.
- [ ] Review account, friends and online flows for explicit connection/reconnection, queue and error feedback, privacy and recovery. Friends blocking/reporting and friend chat are listed as missing; decide product scope and implement or clearly communicate it. Evidence: `docs/application/BACKEND.md`, `godot/ui/friends_page.gd`.
- [ ] **Verify** loading and feedback for a computer capture and ruleset-specific actions. Known notes say Battle AI captures require the human to start the duel and AI levels have not been calibrated with people. Evidence: `godot/chess/ai/README.md`, `DEVELOPMENT_STATUS.md`.

### Audio and feel

- [ ] Review music, castle ambience, footsteps, armor, impacts, torches and UI sounds together on headphones and speakers; tune loudness, spatial falloff, repetition and transitions so effects do not mask gameplay. Current audio is generated and has not received a real-device listening pass. Evidence: `docs/audio/AUDIO.md`, `godot/combat/audio/combat_audio.gd`.
- [ ] Add or verify separate music/effects volume controls, mute and accessibility behavior, including background/resume and scene changes. The status notes list a music slider as unfinished; confirm settings before implementation. Evidence: `godot/ui/settings_page.gd`, `godot/ui/application_settings.gd`.
- [ ] **Verify** controller rumble and Android haptics/permissions and add user controls if supported; the documented controls have not been tested with physical devices. Evidence: `godot/combat/CONTROLS.md`, `godot/combat/TOUCH.md`.

## P2 — Quality bar and content completeness

- [ ] Establish a reference visual target and compare the live game at consistent camera positions: title, setup, 2D/3D opening board, selected piece, capture, duel, victory, online lobby and settings. Capture current desktop and Android screenshots/video; the checked-in examples may show older UI and models.
- [ ] Profile CPU/GPU time, draw calls, asset and texture memory, load time, battery and thermals on representative low/mid/high devices. Set and verify frame-time budgets for each graphics preset; prevent effects from obscuring the board. Evidence: `godot/ui/platform_input.gd`, `godot/tests/paladin_memory_test.gd`.
- [ ] Check transitions and input when the app loses focus, rotates, changes resolution, enters/exits fullscreen, disconnects a controller, backgrounds during a duel or runs out of network; restore control without double moves or a stuck overlay.
- [ ] Review animation for promotions, castling, en passant, check/checkmate, draw, interrupted moves and repeated matches; confirm 2D and 3D are consistent with authoritative chess state. Expand human review beyond automated state assertions.
- [ ] Review localizations and text expansion, font coverage, readable small-screen labels and long account names. Establish a localization workflow if international release is intended.
- [ ] Replace outdated or contradictory documentation and screenshots with the current build and actual mode support; label historical notes. In particular, do not present an old screenshot or old pit-world limitation as current evidence without reproducing it.
- [ ] Maintain a release checklist with exact build commit, passing CI, known failures, device coverage, artifact signatures and accessible download links. Automated tests can reduce regressions; they cannot establish art quality or replace human playtesting.
